# ADR-011: PostgreSQL Owns Core Records While MongoDB Retains Integrations

## Context

Core account, event, response, attendee, signup, group, and folder data live in MongoDB while PostgreSQL already owns new anonymous events under [PostgreSQL Anonymous Event Compatibility Contract](../../../../server/docs/postgres-anonymous-event-compatibility.md).
The repository must make one store authoritative per migrated record, must avoid permanent dual writes, and must not let retained integration documents remain a second account authority.
Calendar connections, provider tokens, calendar preferences, OTP challenges, friend requests, and historical daily user logs have no PostgreSQL target and must keep working.

## Considered Options

- Keep MongoDB authoritative for all core data and leave PostgreSQL as an anonymous-event exception.
- Move every MongoDB collection, including calendar integrations and historical logs, into PostgreSQL.
- Make PostgreSQL authoritative for core records and retain MongoDB only for integrations keyed by the legacy account identity.
- Write each mutation to both stores during a transition period.

## Decision Outcome

Chosen option: "Make PostgreSQL authoritative for core records and retain MongoDB only for integrations", because it gives each migrated record one authority, keeps unchanged integrations working, and avoids a permanent dual-write path.
PostgreSQL owns accounts and profiles, all event kinds, responses, attendees, signup data, availability groups, folders, and folder membership.
MongoDB retains calendar connections and provider tokens, calendar preferences, OTP challenges, friend requests, and historical daily user logs.
Each retained document keeps the legacy account identifier and resolves it through `platform_identities.external_user_id`, and no retained document may create, merge, rename, or authorize an account.

## Consequences

- Good, because a core record has exactly one authority and the migration can enforce it per record kind.
- Good, because unchanged integration and historical data avoid a risky rewrite.
- Bad, because requests that combine core and integration data must join across stores through the account mapping.
- Bad, because the retained MongoDB account document becomes integration-only and profile-dependent consumers must read PostgreSQL.
