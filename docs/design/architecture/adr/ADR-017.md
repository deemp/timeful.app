# ADR-017: Backfill Retained Data On The Migration Ledger And Remove MongoDB In Dependency Order

## Context

The retained record kinds must move to PostgreSQL without a permanent dual-write path, and MongoDB must be removed only after every record kind is authoritative in PostgreSQL.
The core migration already established a resumable batched backfill with a short write freeze, a migration ledger, reconciliation, and unmodified source retention in [ADR-013](ADR-013.md).
The retained record kinds need the same guarantees plus provider-credential re-encryption and a removal order that never strands data.

## Considered Options

- Copy retained data in one offline dump during a maintenance window.
- Dual-write calendar, OTP, and daily-log mutations until an eventual cutover.
- Reuse the ledger-based resumable backfill per retained kind, then remove MongoDB in dependency order.
- Remove MongoDB immediately after the core cutover without migrating retained data.

## Decision Outcome

Chosen option: "Reuse the ledger-based resumable backfill per retained kind, then remove MongoDB in dependency order", because it extends the proven core mechanism, keeps the source authoritative until each kind is validated, and makes removal a series of gated stages.

Each retained unit is written in one PostgreSQL transaction that also records completion in the existing `migration_ledger`, keyed by `(kind, legacy_id)`, so reruns skip completed units and never duplicate a record.
Owners resolve through `platform_identities.external_user_id`, a unit without an owner account is quarantined as `missing-owner-account`, and no step creates an account from a retained document.
The backfill decrypts legacy AES-CFB credentials and re-encrypts them with the authenticated envelope from [ADR-015](ADR-015.md), and reconciliation verifies the round-trip.
After catch-up, each kind enters a short write freeze, runs a final idempotent pass and reconciliation, and then becomes PostgreSQL-authoritative.
OTP challenges are not backfilled because they expire in ten minutes; the cutover takes writes in PostgreSQL and drains the expiry window.

Removal is ordered and gated: calendar cutover, OTP cutover, daily-log cutover, analytics read switch, friend-request retirement, retained-document removal, and only then the MongoDB runtime, driver, configuration, and collections.
The schema is additive, downgrades are refused during migration, and the retained source stays unmodified until the retention window and final validation complete.
The final MongoDB removal requires a validated core-record cutover, a validated retained-data cutover, an unexpired retention window, and verified backups.

## Consequences

- Good, because one backfill and reconciliation pattern covers both core and retained data.
- Good, because rollback before a freeze is a routing change back to the untouched source.
- Good, because removal is staged so a failed stage never requires recovering already-dropped data.
- Bad, because the write freeze remains the practical point of no return for each kind.
- Bad, because the final MongoDB removal is irreversible and depends on operational discipline.
- Bad, because the migration ledger and quarantine tables must be retained and then dropped on schedule.
