# ADR-013: Cut Over By Resumable Backfill With A Short Write Freeze

## Context

Core data must move from MongoDB to PostgreSQL without a permanent dual-write path and with clear recovery and rollback limits.
The migration must be resumable, idempotent, and reconcilable against the untouched source, and the repository must keep MongoDB authoritative until each record kind is validated in PostgreSQL.

## Considered Options

- Take an offline dump and reload PostgreSQL during a long maintenance window.
- Write every mutation to both stores until an eventual cutover.
- Run a resumable batched backfill, re-copy changed records, then freeze writes briefly for a final pass and cutover.

## Decision Outcome

Chosen option: "Run a resumable batched backfill, re-copy changed records, then freeze writes briefly for a final pass and cutover", because it keeps the source authoritative during backfill, avoids permanent dual writes, and bounds the interruption to a short, verifiable window.
Each aggregate is copied in one PostgreSQL transaction that also records completion in the migration ledger, so a rerun skips completed units and never duplicates a record.
A bounded catch-up pass re-reads changed source records while MongoDB writes continue.
The application then enters a short write freeze for the migrating record kind, rejects or queues new mutations without dual-writing them, runs a final idempotent pass and reconciliation, and switches that kind to PostgreSQL.
Records are cut over in dependency order: accounts, then events with responses and attendees and signup data, then folders and folder membership.
The schema is additive, destructive downgrades are refused, and MongoDB source documents stay unmodified until the retention window and final validation complete.

## Consequences

- Good, because rollback before a cutover is a routing change back to the untouched MongoDB source.
- Good, because the interruption window is short and gated by reconciliation evidence.
- Bad, because the write freeze is the practical point of no return for a cutover kind, since post-freeze PostgreSQL writes are not dual-written.
- Bad, because operators must run and verify a migration ledger, catch-up pass, and reconciliation before each cutover.
