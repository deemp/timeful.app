# ADR-015: Encrypt Provider Credentials At Rest With Authenticated AES-256-GCM

## Context

Calendar connections carry OAuth2 access and refresh tokens, Apple app passwords, and ICS feed URLs that may embed private tokens.
These credentials currently live in the retained MongoDB `users` document.
The Apple password is already encrypted with the legacy AES-CFB helper in `server/utils/utils.go`, but that construction is unauthenticated, so a tampered ciphertext is not detected, and the refresh token, access token, and ICS feed URL are stored in plaintext.
Moving the credentials to PostgreSQL is the point at which the repository must fix a single, authenticated at-rest format and a decryption failure policy.

## Considered Options

- Keep the legacy AES-CFB helper for the PostgreSQL credentials.
- Store credentials in plaintext and rely on database access controls.
- Define a new authenticated AES-256-GCM envelope keyed by `ENCRYPTION_KEY`, with versioning and fail-closed decryption.
- Encrypt the whole calendar row and lose queryability of non-secret fields.

## Decision Outcome

Chosen option: "Define a new authenticated AES-256-GCM envelope keyed by `ENCRYPTION_KEY`, with versioning and fail-closed decryption", because it detects tampering, keeps non-secret fields queryable, and gives one boundary for every provider secret.
Credentials are encrypted with AES-256-GCM using a fresh 96-bit random nonce and a 128-bit tag, and are stored as the versioned envelope `v1:` plus base64 of `nonce || ciphertext || tag`.
The key is the `ENCRYPTION_KEY` environment variable read as exactly 32 raw bytes, validated at startup, and never logged.
Encrypted fields are the OAuth2 access token, the OAuth2 refresh token, the Apple password, and the ICS feed URL; expiry, scope, email, picture, enabled state, sub-calendars, and calendar preferences are not secrets and stay plaintext.
A decryption failure is returned as an error and never yields an empty credential or falls back to the retained document.
The backfill decrypts legacy AES-CFB values and re-encrypts them with the GCM envelope, and request paths read and write only the GCM envelope.
Credentials are never serialized into an API response.

## Consequences

- Good, because tampered or truncated credential ciphertext is detected instead of silently decrypted.
- Good, because one versioned boundary covers every provider secret and admits a future key rotation without ambiguity.
- Good, because non-secret fields remain queryable for refresh scheduling and listing.
- Bad, because a missing or wrong-length `ENCRYPTION_KEY` now refuses to start rather than deriving a key.
- Bad, because the legacy AES-CFB format must be decoded once during backfill, keeping the old helper alive until the migration completes.
- Bad, because losing the key makes existing credentials unrecoverable and requires re-authentication.
