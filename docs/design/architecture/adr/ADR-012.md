# ADR-012: Resolve Legacy Accounts By external_user_id And Rewrite Migrated Relationships

## Context

Migrated records reference legacy MongoDB account and event identifiers.
The repository must resolve retained MongoDB references such as calendar connections, friend requests, and daily user logs to the same account, and it must not create duplicate account identities.
Public event URLs are explicitly allowed to change, so the design does not need a permanent compatibility map for event identifiers.

## Considered Options

- Keep a permanent generic legacy-identifier table for every migrated entity and reference.
- Preserve every legacy event identity so that all old links keep resolving.
- Map accounts through `platform_identities.external_user_id` and rewrite migrated relationships during migration.
- Store legacy identifiers as extra columns on each PostgreSQL table.

## Decision Outcome

Chosen option: "Map accounts through `platform_identities.external_user_id` and rewrite migrated relationships during migration", because it satisfies duplicate-free account resolution, keeps request paths free of a compatibility lookup, and matches the allowed change of public event URLs.
`platform_identities.external_user_id` holds the hexadecimal legacy account identifier and is created idempotently through `FindOrCreatePlatformIdentity`.
Distinct legacy accounts remain distinct accounts even when their emails compare equal, because merging them would infer an identity the source does not establish.
Migrated events, responses, blocks, attendees, folders, and memberships receive new PostgreSQL identities, and every relationship among them is rewritten in the same migration transaction.
A temporary, migration-scoped ledger keyed by the legacy identifier provides resumability and idempotency, is never read by request paths, and is dropped after cutover validation.
Sessions keep their cookie-held legacy account value and resolve the PostgreSQL account through the mapping.

## Consequences

- Good, because account references resolve without a permanent compatibility table.
- Good, because migrated schema stays clean and request paths have no second lookup.
- Bad, because old public event URLs stop resolving or resolve to a new identifier after cutover.
- Bad, because resumable migration depends on a temporary ledger that must be dropped on schedule.
- Bad, because equal-email legacy accounts are not merged, so duplicate-looking accounts can persist by design.
