## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented TASK-0190.06 without any live or production migration. Tooling lives at server/scripts/20260910_mongo_events_to_postgres/ and writes only PostgreSQL; the MongoDB source is never modified.

Schema: server/migrations/20260910170000_migration_ledger.sql adds migration_ledger (unique kind+legacy_id with target_id and batch) and append-only migration_quarantine (unique kind+legacy_id+reason). Both use UUID primary keys with gen_random_uuid() so the application role needs no sequence grants.

Units: events with responses, signup blocks/responses, and attendees; then folders with memberships. Each unit commits in one transaction that also records the ledger entry, so a rerun skips completed units and resumes after the first incomplete one. --limit stops after N committed event units and defers folders/reconciliation to a completing run.

Identity: authenticated event owners resolve owner_external_id plus owner_platform_identity_id through platform_identities; account responses and account signups associate a fresh Event Visitor Identity with the account so existing access survives. Guest responses get an unassociated visitor identity, no EVCC, and no owner token; legacy guestEditToken values are quarantined and never imported as authority.

Quarantine reason codes implemented: missing-owner-account, incomplete-token-ownership, missing-response-identity, invalid-guest-name, orphan-response, orphan-membership, and legacy-guest-credential. Reconciliation verifies per-kind counts, num_responses equality, signup block claims, folder membership, and quarantine totals.

Runbook: server/docs/postgres-core-migration-runbook.md documents source-write coordination (batch, catch-up, freeze, final pass, cutover), resumability, reconciliation evidence, quarantine handling, cutover gate, rollback boundaries, retention, and ledger drop.
<!-- SECTION:NOTES:END -->
