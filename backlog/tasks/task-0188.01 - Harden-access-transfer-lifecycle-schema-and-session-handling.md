## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Server-side follow-ups from the TASK-0071.02 review. The transfer lifecycle has two functional gaps: open rejects approved-but-unredeemed transfers so a target that reloads the link cannot redeem, and cancel only works in pending state so the source cannot stop an approved transfer. Data hygiene and schema also need hardening: expired rows are never pruned, approved_request_id has no foreign key, session redemption clears the whole session, and transfer/grant cookies use SameSite=Strict while the base EVCC cookie uses Lax. Keep approval single-use and source-confirmed, keep redemption gated on the target proof and the exact approved request, and keep MongoDB behavior unchanged.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Opening a transfer link for an approved-but-unredeemed transfer returns the approved request and matching code to the browser holding the target proof without granting authority before redemption
- [ ] #2 Source cancel succeeds for pending and approved-but-unredeemed transfers and a cancelled transfer rejects subsequent approval and redemption
- [ ] #3 Redeem replaces only the session identity and unrelated session keys survive the transfer
- [ ] #4 Expired access transfers are pruned automatically together with their requests without removing live transfers
- [ ] #5 A migration enforces approved_request_id as a foreign key to access_transfer_requests
- [ ] #6 Transfer and grant cookie attributes match the base EVCC cookie or a code comment documents the intended difference
- [ ] #7 Route tests cover open-after-approval redemption, cancel-after-approval blocking redemption, and pruning, and the existing rejection matrix stays green
