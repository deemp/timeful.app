## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Implement the account deletion behavior that docs/requirements/functional/fr/FR-123.md defines so the system has one ratified deletion contract instead of the current split between the UI promise, the AC wording, and the route implementation.

Context
The Settings delete-account action currently calls DELETE /api/user, which removes the PostgreSQL account row and the retained MongoDB integration document, then clears the session. It leaves the platform identity mapping behind, does not release ownership of the events the account organized, and performs no cleanup of the visitor's own responses, friend requests, folders, or historical logs. The two-store delete is not atomic, is not idempotent, and a concurrent account backfill can recreate an account that is being deleted. The UI copy "All your account data will be lost" does not match the actual outcome.

Ratified behavior (FR-123)
- A signed-in visitor confirms deletion by entering the account email address.
- Deletion is immediate and permanent: the visitor is signed out, the account profile and platform identity mapping are removed, and every calendar connection and its provider credentials are disconnected.
- Events the account organized survive with ownership released and keep their other guests' responses.
- The deleted visitor's own responses, friend requests, folders, and historical user logs are removed.
- No data is retained, recovered, or exported after deletion.
- Signing in with the same email afterward creates a new account and a new platform identity.
- Deletion is atomic and idempotent across stores.

Scope
- Rework the delete path in server/routes/user.go, server/accounts, server/postgres, and server/db so the ratified behavior is applied as one unit.
- Remove the platform identity mapping and ensure a fresh sign-in cannot resurrect the deleted account or leave an orphan identity.
- Release ownership on events the account owned while preserving those events and other guests' responses.
- Remove the visitor's own responses, folders and memberships, friend requests, and historical logs.
- Make the delete atomic across PostgreSQL and MongoDB and safe to retry.
- Prevent a concurrent account backfill from recreating an account that is being deleted.
- Update the Settings delete-account copy to describe the ratified outcome.
- Add regression tests for each behavior, including the partial-failure and concurrent-backfill cases.

Do not expand into the unrelated account contract test coverage of TASK-0190.02.06; that task consumes this behavior once it lands.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## Delivery Model

Keep the work as one reviewable deliverable on this task; do not split by store or create new tasks.
FR-123 makes deletion atomic by contract and AC4/AC6 depend on it, so partial delivery would violate the requirement rather than progress toward it.

## Decisions

- Cross-store atomicity: PostgreSQL deletion tombstone keyed by `external_user_id` plus a `pg_advisory_xact_lock(hashtextextended(external_user_id,0))` shared with account creation. Ordered idempotent cleanup: MongoDB first, PostgreSQL transaction last.
- Backend enforces email confirmation; `DELETE /api/user` binds and verifies the account email.
- Historical daily user logs: pull the account id from `userIds`, then delete a log only when no users remain.

## Phase 1 - Schema

- Add `server/migrations/…_account_deletion.sql` with `account_deletion_tombstones(external_user_id TEXT PRIMARY KEY CHECK (external_user_id <> ''), deleted_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp())`.
- Tombstone is inserted in the same PostgreSQL transaction that removes the account and platform identity, so deletion is idempotent and resurrection-safe.

## Phase 2 - PostgreSQL Repository

- `server/postgres/accounts.go`, `server/postgres/identities.go`:
  - `FindOrCreateAccount` and its identity creation take the advisory lock, then no-op with `ErrAccountDeleted` when tombstoned (AC6).
  - `DeleteAccountByExternalUserID` becomes a transaction: release `postgres_events` ownership (null `owner_platform_identity_id`, `owner_external_id`, `owner_event_visitor_identity_id`) while keeping events (AC2); delete the account's `postgres_event_responses` via `event_visitor_identities.platform_identity_id` plus legacy `account_user_id` (AC3); delete account-associated `event_visitor_identities` after clearing owner pointers and transfer references (credentials cascade); delete `accounts` and `platform_identities` rows (AC1); insert the tombstone.
- Block new identity association for an external id while its deletion is in flight.
- Update `TestAccountRepositoryUpdatesAndDeletesProfileOnly` and test cleanup helpers that currently assert the identity and integration document are retained.

## Phase 3 - MongoDB Cleanup And Orchestrator

- New `server/db` cleanup: idempotently delete `eventResponses` by `userId`, `folders` plus `folderEvents` by `userId`, `friendrequests` from/to, pull from `dailyuserlogs.userIds` then delete empty logs, `$unset events.ownerId`, and delete the retained `users` integration document (AC2/AC3).
- `accounts.DeleteAccount(ctx, externalUserID)` orchestrates MongoDB cleanup first (retry-safe while the account and session still resolve), then the PostgreSQL transaction. A partial failure leaves the account authority intact and retry converges (AC4).
- Add an injectable function-typed seam (small `Deleter`) so a forced MongoDB cleanup failure proves retry leaves no partial state.
- Confirm `FindOrCreatePlatformIdentity`/`ResolveForSignIn` create a fresh external id and account for the same email after deletion (AC5).
- Ensure `server/scripts/20260910_mongo_accounts_to_postgres` skips tombstoned accounts.

## Phase 4 - Route And Frontend

- `server/routes/user.go` `deleteUser`: bind `{email}`, compare case-insensitively to the account email, run the deletion unit, clear the session only on success (AC7, FR-123).
- `frontend/src/views/Settings.vue`: send `{ email: deleteValidateEmail }` and replace the copy with the ratified outcome (profile and identity removed, calendars disconnected, organized events survive without ownership, own responses/friend requests/folders/logs removed, sign-in creates a new account).

## Phase 5 - Tests And Checks

- `server/postgres/accounts_test.go`: tombstone no-op, ownership release, response and visitor removal.
- `server/routes/accounts_test.go`: full cross-store deletion, email mismatch rejection, idempotent retry, partial-failure retry, concurrent backfill race, re-sign-in creates a fresh account and identity (AC8).
- `server/scripts/20260910_mongo_accounts_to_postgres/main_integration_test.go`: backfill after deletion skips tombstoned accounts.
- `frontend/src/views/Settings.test.ts`: copy and email payload.
- Run `go build ./...`, `go vet ./...`, and the isolated `server-route-test` suite; run frontend `lint`, `fmt:check`, `typecheck`, `build`, `test:unit`; then `graphify update .`.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented the deletion unit as planned: `postgres.DeleteAccountByExternalUserID` now runs one transaction that takes `pg_advisory_xact_lock(hashtextextended(external_user_id,0))`, deletes the account's transfers, releases event ownership, deletes the account's responses and visitor identities, removes the account and platform identity, and inserts the `account_deletion_tombstones` row.

`FindOrCreatePlatformIdentity` now takes the same advisory lock and returns `ErrAccountDeleted` for a tombstoned identifier, so a concurrent or repeated account backfill cannot resurrect a deleted account. The backfill script treats that as a skip.

Added `db.DeleteAccountData` for the ordered, idempotent MongoDB cleanup and `accounts.Deleter` / `SetDefaultDeleter` as the injectable cross-store orchestrator; MongoDB cleanup runs first, the PostgreSQL transaction last, and the session is cleared only after the whole unit succeeds.
