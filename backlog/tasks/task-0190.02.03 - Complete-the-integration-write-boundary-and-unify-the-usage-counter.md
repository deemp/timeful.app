## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Calendar and token data must stay in the retained MongoDB integration document without touching PostgreSQL profile authority, and num_events_created must have a single source of truth. One calendar write still bypasses the integration-only helper, and the profile read path replaces the PostgreSQL counter with a MongoDB-derived count, contradicting the field ownership declared in the migration contract.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->

- [x] #2 The profile response num_events_created comes from one authoritative source, and a profile update cannot change or reset the stored counter.
- [x] #3 Account upserts do not perform needless row updates when the account already exists.
- [x] #4 Tests cover calendar removal, a profile update preserving the counter, and the counter read/write source.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Route calendar-account removal through the integration-only write boundary: add a `db` helper that removes one `calendarAccounts` key with the existing atomic `$setField`/`$$REMOVE` pipeline, and call it from `removeCalendarAccount` instead of the inline `UsersCollection.UpdateByID`.
2. Make `num_events_created` single-sourced: stop overwriting the PostgreSQL account counter in `getProfile` with the MongoDB-derived `GetEventsCreatedThisMonth` count, keeping `UpdateAccountProfile` from writing the counter.
3. Make `FindOrCreateAccount` idempotent without a needless row update: `ON CONFLICT (platform_identity_id) DO NOTHING` and return the stored row.
4. Add regression tests: route-level calendar removal (integration fields only, PostgreSQL profile preserved) and profile counter authority/preservation; repository-level repeat-upsert no-update (xmin) and profile-update-preserves-counter.
5. Run gofmt/go vet and the isolated Compose backend suite.
<!-- SECTION:PLAN:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Closed the last integration-write gaps and made the usage counter single-sourced.

What changed
- `server/db/users.go`: added `RemoveUserCalendarAccount`, the key-removal half of the integration-only write boundary, which atomically removes one `calendarAccounts` key with `$setField`/`$$REMOVE` and never touches the PostgreSQL profile.
- `server/routes/user.go`: `removeCalendarAccount` now calls `db.RemoveUserCalendarAccount` instead of an inline `UsersCollection.UpdateByID`; `getProfile` no longer overwrites the authoritative PostgreSQL counter with the MongoDB-derived `GetEventsCreatedThisMonth` count.
- `server/db/events.go`: removed the now-unused `GetEventsCreatedThisMonth`, so no MongoDB-derived count can be reintroduced as the profile counter.
- `server/postgres/accounts.go`: `FindOrCreateAccount` uses `ON CONFLICT (platform_identity_id) DO NOTHING` so a repeat upsert does not rewrite the stored account row.
- `server/postgres/identities.go`: `FindOrCreatePlatformIdentity` uses `ON CONFLICT (external_user_id) DO NOTHING` with a `WITH inserted`/`UNION ALL` fallback that still returns the existing identity, so account upserts no longer perform a needless identity update either.

Tests
- `server/routes/accounts_test.go`: `TestAccountCalendarRemovalWritesIntegrationOnly` proves removal deletes only the retained key and leaves the PostgreSQL profile and usage counter unchanged; `TestAccountProfileCounterIsPostgresAuthoritative` proves the profile reports the PostgreSQL counter and a name update preserves it.
- `server/postgres/accounts_test.go`: `TestFindOrCreateAccountDoesNotUpdateExistingRow` uses `ctid` to prove a repeat upsert rewrites neither the account nor its platform identity; `TestUpdateAccountProfilePreservesUsageCounter` proves a profile update cannot reset the counter.
- Verified `ctid` changes on `DO UPDATE` and is stable on `DO NOTHING` in a live transaction, so the no-update test is a real regression.

Evidence
- `docker compose --env-file .env.test -f compose.yaml -f compose.test.yaml run --rm server-route-test`: all packages pass.
- `go build ./...`, `go vet ./...`, and `gofmt` clean on changed Go files.
- `npm run format:markdown:check` passes. No authored Markdown changed, and no browser-E2E spec exercises calendar removal or the profile counter, so browser E2E is not required (backend route tests provide the evidence).
