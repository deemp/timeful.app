## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Frontend follow-ups from the TASK-0071.02 review on the target and consent flows. The target transfer page strands users: after the source approves, reloading the link shows a generic expired/unavailable error with no way to redeem an otherwise valid transfer, and redeeming a session transfer silently replaces an existing sign-in with the source account. GrantedAccessConfirmation re-queries every browser-stored event identity on every event navigation because events answered without a consent requirement are never cached. The target-refresh restoration depends on TASK-0188.01 exposing approved state to the proven target browser.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan (approved by user 2026-09-09)

### Decided semantics (user decisions, do not re-litigate)
- AC#2 uses **Option B: server-enforced 409 confirm gate**. Redeem returns `409 {accountSwitchRequired: true}` when it would replace a **different** existing session identity and the body lacks `confirmAccountSwitch: true`. Frontend shows a confirm dialog and re-posts. Fail-closed, precise, no identifier leakage. (Alternatives A: expose sessionTransfer flag on open; C: frontend-only superset — were rejected.)
- AC#1 gets a **small approved-state hint** in the view (not identical-to-initial UI) plus regression coverage.
- E2E covers **both** the refresh-restore scenario (AC#5) and the account-switch confirmation dialog.
- UX semantics for the switch (settled): redemption REPLACES the session identity (sign in as the source/"old" account on this device) — it does NOT make the already-signed-in ("new") account a second owner; no account merging; the new account's data and other device sessions are untouched. Confirmation dialog must state exactly this. **No confirmation when the target's current session is the SAME account** the transfer would install (no actual switch).

### Research findings (current state)
- TASK-0188.01 (commit 63eae4e4, Done) already made server `open` re-serve `{requestId, code, state: "approved"}` to the browser holding the target proof (server/routes/postgres_transfers.go:213). `AccessTransfer.vue` onMounted already re-calls `open` and displays the returned code, so the reload-restore likely already works end-to-end; needs the approved hint + regression coverage (unit + e2e) to prove it.
- The target page CANNOT detect a session transfer today: `open` exposes nothing about transfer mode; `/auth/status` returns `{}` only; guest/owner redemptions never touch the session (grant cookie only); only session-mode redeem changes the session (`session.Set` at postgres_transfers.go:340).
- `store.authUser` is globally populated (App.vue calls fetchAuthUserProfile) — view can name the current account.
- GrantedAccessConfirmation.vue (mounted globally in App.vue:6) re-queries on every event navigation because only `dismissed`/`pending` guard re-queries; events answered `confirmationRequired:false` and erroring events (403 stale records) re-query forever.

### 1. Server — server/routes/postgres_transfers.go
- Extend the redeem input struct with `ConfirmAccountSwitch bool` (json `confirmAccountSwitch`).
- In the `redeem` case, BEFORE creating credentials/consuming state: if `transfer.ExternalUserID != nil`, read `current, _ := sessions.Default(c).Get("userId").(string)`; if `current != "" && current != *transfer.ExternalUserID && !input.ConfirmAccountSwitch` → signal a "switch required" outcome (captured var + early `return nil` inside the transaction closure; no transfer state change, nothing saved). After `WithTransaction` returns, when the flag is set, respond `c.JSON(409, gin.H{"accountSwitchRequired": true})` and return — before the generic error path and before cookie/redirect logic. Must preserve the existing previousCookies restore semantics and the session-save-rollback guarantee (409 happens before any save).
- Update the swag action description/annotation (`@Failure 409`) accordingly.
- Update server/routes/postgres_transfers_test.go: session-mode redeem calls that run while the target holds a different sign-in (including the two concurrent redemption goroutines that currently post `{}`) must post `{"confirmAccountSwitch":true}`; add assertions that redeem WITHOUT the flag returns 409, leaves the transfer in `approved` state (source `status`), and leaves the target session identity unchanged; guest/owner redeem (no session) and same-session redeem stay ungated.

### 2. Swagger / API types regen
- From `server/`: `go run github.com/swaggo/swag/cmd/swag@v1.16.6 init --parseDependency`; from `frontend/`: `npm run gen:api`. RawAccessTransfer is hand-written (frontend/src/types/transport.ts:666) — no shape change needed for the 409 (it is an error body read off FetchError).

### 3. Frontend boundary — frontend/src/composables/transfer/transferBoundary.ts
- Change `transferAction`'s optional 4th param from `selection?: { requestId: string; code: string }` to a merged payload shape `{ requestId?: string; code?: string; confirmAccountSwitch?: boolean }` (approve still passes `{requestId, code}` from matchingRequest; redeem passes `{confirmAccountSwitch: true}`). Keep decodeTransfer unchanged.

### 4. Target view — frontend/src/views/AccessTransfer.vue
- Track the open response: when `state === "approved"` show a subtle approved hint (e.g. "Approved — you can continue") alongside the code (AC#1 visible restoration).
- `finish()`: on redeem catching `FetchError` with `status === 409 && parsed?.accountSwitchRequired` → open a Vuetify confirm dialog (keep inside this view component) stating the switch: title e.g. "Switch accounts on this device?"; body names the current account from `store.authUser` (first/last name, email) and states that continuing signs this browser in as the account that created the transfer, replacing the current sign-in, that the current account stays intact and can be signed back into; Cancel = no redemption (transfer stays approved until expiry); Confirm → re-post redeem with `confirmAccountSwitch: true` → navigate to `/e/{eventId}`. Other errors keep the existing generic message. Use `useMainStore` for authUser.
- Do not name/leak the destination account (unknown to the frontend by design).

### 5. Consent caching — frontend/src/components/event/GrantedAccessConfirmation.vue
- Replace the `dismissed` Set with an `inspected` Set<string> marked synchronously when an event's query starts (before await), so concurrent watch triggers never double-query; skip ids in `inspected`; clear `pending` + `inspected` when `userId !== previous?.[0]` (per-sign-in lifecycle). Dismissal just shifts `pending`. Keep the stale-guard for pushing results. Accepted edge (documented): if a watch trigger goes stale mid-query, that event's result is dropped and it stays "inspected" until the next sign-in — satisfies "at most once per sign-in".

### 6. Unit tests (AC#4)
- New frontend/src/views/AccessTransfer.test.ts (happy-dom, Vuetify stubs like EventAccessTransfer.test.ts): reload/refresh path (open returns `{state:"approved", code}` → code + hint rendered, redeem callable); 409 switch flow (first redeem 409 → dialog appears stating switch → confirm re-posts with confirmAccountSwitch:true → navigates; cancel does not re-post); generic error path unchanged.
- Extend GrantedAccessConfirmation.test.ts: navigation to another event without a consent requirement does not re-query; each stored event queried at most once per sign-in including erroring events; sign-out/sign-in reset re-enables querying.
- Extend transferBoundary.test.ts: redeem posts `{confirmAccountSwitch:true}` when requested; approve payload unchanged.
- Server route tests as in step 1.

### 7. E2E — e2e/specs/timed-event-access-transfer-firefox.spec.ts (AC#5 + agreed dialog coverage)
- New test (guest mode): create event + source response via API, create transfer via API, target opens link in page (target proof cookie lands in context), source approves via API with the on-page code, `targetPage.reload()` → matching code still shown (restored state + approved hint), click "Continue after approval" → lands on `/e/{eventId}` with granted access visible.
