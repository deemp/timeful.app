## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Implement availability-group response mutation on PostgreSQL events and keep calendar-derived and manual availability correct using retained MongoDB calendar integrations. Response save and delete toggle attendee decline state, merge manual availability using the existing day-window replacement semantics, and persist calendar-derived mode, selected calendars, and copied calendar preferences in the response payload. Calendar availability reads resolve each PostgreSQL response's account through the explicit legacy account mapping to the retained MongoDB calendar connection and preserve existing redaction of other members' event names. Authorization reuses the same explicit-selection and Event Visitor Control Credential contract as other PostgreSQL events.

Provider tokens and calendar preferences stay in MongoDB and must not become a second PostgreSQL authority. Depends on TASK-0190.05.02 for group lifecycle and attendee persistence.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Extend the PostgreSQL group path (TASK-0190.05.02 + postgres response store) with group response mutation and calendar-derived availability. Legacy MongoDB group response behavior is the reference; group responses reuse `postgres_event_responses` and the manual availability window stays in the event payload.

Deliverables
1. `server/routes/postgres_event_routes.go`: add calendar/manual fields (`useCalendarAvailability`, `enabledCalendars`, `manualAvailability`, `calendarOptions`) to `postgresResponseInput`; branch `postgresMutateResponse` to `postgresMutateGroupResponse` for `EventTypeGroup`.
2. `server/routes/postgres_group.go`: implement `postgresMutateGroupResponse` under the explicit-selection contract. Create requires proven visitor authority, persists account respondents with `respondent_kind=account`/`account_user_id`/email and anonymous respondents with the canonical guest name; save/rename/delete require the opaque `responseId` and `visitor.controls`. Save sets the attendee `declined=false`, delete sets `declined=true` for the respondent's account email, and both keep `num_responses` correct. Persist `useCalendarAvailability`, `enabledCalendars`, and `calendarOptions` in the response payload. Add `mergeGroupManualAvailability` implementing the legacy day-window replacement (existing day inside `[payloadDay, payloadDay+duration)` is replaced by the payload day, leftover payload days are added).

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
PostgreSQL availability-group response mutation and calendar-derived availability are implemented, with the frontend group submission wired to the same contract.

Backend:
- postgresMutateResponse routes group events to postgresMutateGroupResponse, which applies the shared explicit-selection contract: create requires proven visitor authority; account respondents persist account_user_id/email, anonymous respondents persist the canonical guest name; save/rename/delete require the opaque responseId and visitor.controls. Save clears the attendee decline state, delete sets it, and both keep num_responses correct.
- useCalendarAvailability, enabledCalendars, and calendarOptions persist in the response payload. Manual availability merges with the legacy day-window replacement, and the boundary accepts both the legacy millisecond/RFC3339 encoding and the frontend ZonedDateTime/epoch-millisecond encoding.
- GET /events/{eventId}/calendar-availabilities now resolves PostgreSQL group respondents through the legacy account mapping to retained MongoDB calendar connections, keys results by the opaque publicId, filters to enabled sub-calendars, and redacts other members' event names.

Frontend:
- encodeVisitorGroupResponseSubmission merges the group calendar/manual fields into the existing visitor selection payload, and useAvailabilityData submits them for PostgreSQL groups using the live sharedCalendarAccounts.
