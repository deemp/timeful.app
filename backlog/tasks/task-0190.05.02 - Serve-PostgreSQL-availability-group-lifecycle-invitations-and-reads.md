## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Route availability-group lifecycle through PostgreSQL: creation, settings and attendee edits, invitations, archive/unarchive, deletion, invite decline, and reads. Creation persists the owner as an attendee and adds invitees while sending the existing invitation emails. Edits diff the attendee set, send the existing added-member and update emails, and remove departed members' responses so response counts stay correct. Reads return attendees, derived responded state, and the existing owner and invitee email visibility, and the signed-in dashboard keeps group responded state correct across PostgreSQL and legacy events with the canonical public identifier.

Creation reuses the existing transition creation flag; no second flag is introduced, and flag removal stays in TASK-0190.07. Legacy MongoDB group behavior stays unchanged for unmigrated events. Depends on TASK-0190.05.01 for attendee persistence.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implementation notes

Routing
- `postgresCreationEnabled` now admits `type=group` under the existing `POSTGRES_ANONYMOUS_EVENT_CREATION_ENABLED` flag; no second flag was added.
- `/events/:eventId/decline` dispatches to the new `postgresDeclineInvite`, which sets attendee decline state with the legacy signed-in authorization. An optional `{"declined": false}` body covers undecline; the frontend's empty-body POST still declines. The legacy `declineInvite` handler carries the Swagger annotation, so the PostgreSQL handler adds none and no route annotation changed.
- `postgresOwnerMutation` now returns a bool so group edit emails run only after a committed owner mutation.

Creation (`postgresCreateEvent`)
- Binds a `postgresEventInput` whose outer `Attendees []string` shadows `models.Event.Attendees` (the persistence attendee shape), so group payloads decode.
- Groups skip timed-payload validation because they persist membership separately.
- Inside the creation transaction the signed-in owner is added as a non-declined attendee and invitees are added (upsert keeps one membership per event and email). Invitation emails (template 9) are sent after commit. The payload never carries a second attendee copy.

Edits (`postgresEditEvent`)
- `postgresApplyGroupAttendeeEdits` diffs requested emails against stored membership, protects the owner from removal, deletes a departed member's account response and decrements `num_responses`, and returns the post-commit email plan.
- Added members get invitation emails (template 9) and kept members get update emails (template 11) after commit, matching legacy ordering.

Reads
- Group reads expose `attendees` (email, declined, PostgreSQL `_id`, eventId) and keep respondent emails visible to the owner and non-declined invitees when `collectEmails` is off, promoting the response email into the rebuilt user snapshot so clients can match pending attendees. Strangers see redacted emails. Timed and signup reads keep their prior behavior.
- The dashboard query now also lists non-deleted PostgreSQL groups where the account's email is a non-declined attendee and derives `hasResponded` from `responded && member`, matching legacy attendee-driven responded state. `_id` and `shortId` stay the canonical PostgreSQL short id, and legacy MongoDB groups merge unchanged.
