## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
First-time sign-in and the first authenticated request both create records: a PostgreSQL account (possibly with a new platform identity) and a retained MongoDB integration document. Under concurrent requests these check-then-create sequences can create duplicate accounts for one email or fail with a duplicate-key error, breaking the duplicate-free account guarantee in FR-121 and ADR-012.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Concurrent first-time sign-ins for the same email resolve to a single PostgreSQL account, or are serialized so that no duplicate account or platform identity is created.
- [x] #2 Concurrent first authenticated requests for the same account do not fail when creating the retained integration document, and create it at most once.
- [x] #3 Tests exercise the concurrent paths and assert no duplicates and no failed requests.
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Deliverables
1. `server/postgres`: add `FindOrCreateAccountByEmail`, which serializes concurrent first-time sign-ins for one case-insensitive email behind a transaction-scoped PostgreSQL advisory lock, re-checks the email after acquiring the lock, and returns the single existing account when another request won the race. Keep `FindOrCreateAccount` idempotent for external-ID adoption.
2. `server/postgres/repository.go`: add a `withTransaction` helper so a repository already bound to a transaction runs the callback in that transaction instead of rejecting it, letting the lock path stay unit-testable.
3. `server/accounts/accounts.go`: route `ResolveForSignIn`'s create path through `FindOrCreateAccountByEmail` and report `created` from the actual outcome.
4. `server/db/users.go`: make `EnsureIntegrationUser` idempotent under concurrency so a duplicate-key insert by a concurrent request is treated as success and the existing document is returned.

Tests
- `server/postgres/accounts_test.go`: concurrent `FindOrCreateAccountByEmail` calls for one email create exactly one account and one platform identity with no errors (AC#1).
- `server/accounts/accounts_test.go`: concurrent `ResolveForSignIn` calls for one email resolve one account (AC#1); concurrent `EnsureIntegrationDocument` calls create the retained document at most once with no failures (AC#2).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented with an email-keyed transaction-scoped PostgreSQL advisory lock. `Repository.FindOrCreateAccountByEmail` takes `pg_advisory_xact_lock(hashtextextended(lower(email), 0))`, re-checks the case-insensitive email inside the lock, and reuses the winner's account when a concurrent request already created it; `ResolveForSignIn` now reports `created` from that outcome so the losing request does not repeat listmonk sign-up. `Repository.withTransaction` lets the lock path run inside an existing transaction for the temp-table unit test. `EnsureIntegrationUser` treats a MongoDB duplicate-key insert as idempotent success and returns the existing document.

Both regression tests were confirmed to fail against the pre-fix behavior: reverting `ResolveForSignIn` to `FindOrCreateAccount` made the boundary test resolve two different accounts, and reverting `EnsureIntegrationUser` made the integration-document test fail with E11000 on `_id`.
<!-- SECTION:NOTES:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Serialized account creation by email and made the retained integration-document insert idempotent so concurrent first-time requests cannot create duplicates or fail.

Changes:
- `server/postgres/accounts.go`: added `FindOrCreateAccountByEmail`, which holds a transaction-scoped advisory lock keyed by the normalized email, re-checks the account by case-insensitive email inside the lock, creates it only when absent, and returns `(account, created, error)`. Distinct pre-existing equal-email accounts stay untouched.
- `server/postgres/repository.go`: added `withTransaction`, which runs the callback in the existing transaction when the repository is already transaction-scoped, so the lock spans the whole check-then-create unit.
- `server/accounts/accounts.go`: `ResolveForSignIn` now uses the lock-backed method and returns the real `created` outcome instead of always `true`.
- `server/db/users.go`: `EnsureIntegrationUser` treats a MongoDB duplicate-key error as idempotent success and returns the document the concurrent winner created.

Tests:
- `server/postgres/accounts_test.go`: `TestFindOrCreateAccountByEmailReusesExistingAccount` (case-insensitive reuse) and `TestFindOrCreateAccountByEmailConcurrentSignIns` (8 workers, one account and one platform identity, no errors).
- `server/accounts/accounts_test.go`: `TestResolveForSignInConcurrentEmailCreatesSingleAccount` (8 workers, one account, exactly one reports creation) and `TestEnsureIntegrationDocumentConcurrentCreatesAtMostOnce` (one retained document, no failures).
